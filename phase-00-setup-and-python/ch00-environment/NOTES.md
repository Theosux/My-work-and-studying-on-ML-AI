## Notes
### 00.1 Git & GitHub: version control workflow
#### The four places inside git are:
Working Tree (files on your disk) - you advance with git add
<br>
Staging Area (a draft of your next commit) - you advance with git commit
<br>
Local Repository (the .git/ folder; HEAD points to the latest commit) - you advance with git push
<br>
Remote(Origin) (a copy on github) - origin is a nickname of the URL

#### .gitignore
.gitignore exists to not commit data or local files meant to not be public, or packages including environment files containing hundreds of MB

#### git add & git commit
Git add doesn't add files to git, it copies the file's current content into the staging area. Editing will mean you have to add again, otherwise the staged copy is an older version
<br>
A commit contains the added stages of your local data (a snapshot in your local repository)

### 00.2 uv environments: reproducible packages
#### Global pip vs uv | the role of pyproject.toml, uv.lock, .python-version and .venv/
A global pip install does not record what the project actually needs
<br>
uv lets another user use uv sync and get the identical environment with the exact versions
<br>
pyproject.toml - Python version range and dependencies - edited by uv add and also by the programmer
<br>
uv.lock - The exact version of every package, generated by uv
<br>
.python-version - Pins of the interpreter
<br>
.venv/ - The packages themselves(never commit)

#### uv commands
uv init - creates the project (pyproject.toml, .python-version)
<br>
uv add numpy - does 3 things at once: writes it in pyproject.toml, pins exact versions in uv.lock, installs it in .venv (uv add --dev pytest for tools only I need)
<br>
uv remove numpy - the reverse
<br>
uv sync - makes .venv match uv.lock exactly: installs what's missing and removes anything not in the lock
<br>
uv run python file.py - syncs, then runs inside .venv, no activation needed, works from any terminal
<br>
Broken env? Delete .venv/ and run uv sync - you get the identical environment back

#### The `uv pip install` trap
uv pip install (or pip install) puts the package in .venv but doesn't record it somewhere (nor pyproject.toml, uv.lock)
<br>
The next uv sync removes it, and somebody who clones the repo will not get it -> always use uv add

### 00.3 Kernels & notebooks: interactive Python
#### Editor, interpreter, kernel
Editor (VS Code) - only shows and edits text, runs no Python
<br>
Interpreter (repo\.venv\Scripts\python.exe) - runs a .py file top to bottom and exits, all variables are gone after
<br>
Kernel - the same interpreter but kept alive by ipykernel; receives cells one at a time and keeps variables in memory between them
<br>
ipykernel is the package that turns a plain interpreter into a Jupyter kernel, that's why it is in my uv add list

#### Kernel state & hidden state
Fresh kernel = empty memory $S_0 = \{\}$, each cell transforms it: $S_n = c_n(S_{n-1})$
<br>
So the memory depends on the execution history, which the .ipynb file does NOT store (it only stores cell code + last outputs)
<br>
Most cells aren't idempotent: $c(c(S)) \neq c(S)$ - running X = X / 255 twice divides pixels by $255^2$, with no error
<br>
Hidden state = results that depend on a deleted/edited cell or cells run out of order (deleting a cell edits the file, not the memory)
<br>
Fix: Restart & Run All before trusting any number or plot. The [n] counters show when each cell ran - reproducible = 1, 2, 3... top to bottom

#### Which Python is running my code?
Check: import sys; print(sys.executable) - should end in repo\.venv\Scripts\python.exe
<br>
Fresh PowerShell python file.py -> global Python on PATH (ModuleNotFoundError)
<br>
uv run python file.py -> always the project's .venv
<br>
VS Code terminal / Run button / notebook -> whatever interpreter or kernel is selected (open a NEW terminal after selecting)
<br>
Always open repo/ as the folder in VS Code, it looks for .venv in the opened folder
<br>
"Install ipykernel?" prompt = wrong kernel selected, .venv already has it -> switch kernel, never click Install (it's a pip install, recorded nowhere)

#### Notebook vs .py (and `# %%` cells)
Notebook - exploring: looking at data, plots next to code, quick experiments, write-ups
<br>
.py - building: reusable functions, anything pytest tests (pytest imports modules, a notebook is JSON), long training runs, clean git diffs
<br>
Rule of thumb: copy-pasted a cell twice -> move it to a .py and import it
<br>
`# %%` lines in a .py mark cells, Shift+Enter runs them in the Interactive Window, but the file stays plain Python
<br>
if __name__ == "__main__": - code inside runs with uv run python file.py but NOT on import, so pytest can import my functions without running the demo

#### Pitfalls
Module cache - editing helpers.py and re-importing does nothing (Python caches it in sys.modules) -> restart kernel or %load_ext autoreload + %autoreload 2
<br>
VRAM - a model/tensor in a notebook variable keeps GPU memory while the kernel lives -> del model + torch.cuda.empty_cache() or restart
<br>
Git noise - notebooks store outputs (images as base64) -> Clear All Outputs or Restart & Run All before committing


## Summary
### 00.1 Git & GitHub: version control workflow
We use git for version control and uv for consistent packages versions control, git has four places inside it, and you can move your files code and data using git add git commit and git push. Origin is a nickname of the URL existent on github and .gitignore is used to exclude certain files from being pushed(sensitive data and also packages)

### 00.2 uv environments: reproducible packages
Each project gets its own .venv/ containing the package, but only pyproject.toml says what you want. Basically anyone can run uv sync to get the identical environment.

### 00.3 Kernels & notebooks: interactive Python
VS Code only edits, the .venv interpreter runs code - as a one-shot script, or kept alive as a kernel (thanks to ipykernel) that remembers variables between cells. The memory depends on the order I ran cells, not the file, so the notebooks can hide state, so Restart & Run All is how I prove a result is real. Notebooks are for exploring, .py files are for code I reuse, test, or train with, and sys.executable tells me which Python is actually running.
